2. 폰 → 서버 — 패킷 손실 27%

구간1920×1440 · 품질 90 · 12장960×720 (진단)
폰 넣음 → 인코딩 → 전송730 = 730 = 730 (VP8 제한 none)—
게이트웨이 패킷 손실약 27% (받음 22,065 · 손실 8,206) · jitter 40~113ms · 폰 PLI 77번/약 70초약 2.8% · jitter 5~14ms
디코딩 (게이트웨이)폰이 보낸 것의 약 87% · 디코딩 실패 05초에 60장 (빠짐 없음)
API 처리받은 만큼 처리 (1675장 중 1674장, decode 2 + PD 11 + QI 25ms)—

폰 인코더·게이트웨이 디코더는 정상이고, 빠지는 곳은 무선 구간이다. HMD → 폰 JPEG(약 27Mbps)가 같은 Wi-Fi 무선 시간을 차지해 폰 → 서버 UDP가 손실된 것으로 본다. 측정용으로 폰 통신 로그에 WebRTC 송신 통계(넣음·인코딩·전송·패킷·재전송·NACK·PLI·서버 보고 손실), 게이트웨이에 video_stats(디코딩·/ws 장수, 패킷 수신·손실, jitter)를 더했다.

결정 (2026-11-10): HMD 영상을 4:3 1440×1080 · JPEG 품질 80 · 초당 10장(약 8Mbps 추정)으로 바꾼다. 1080p 이상(API §5.5)은 지킨다. 서버가 보는 화질은 폰 VP8(한 장 약 25~40KB)이 정하므로 품질 80은 서버 쪽 화질에 거의 영향이 없다. 초당 10장이면 같은 장수 규칙(확정 5장 · 면 5장)이 약 0.5초가 된다.

3. 열린 문제 — 제품이 실제보다 많이 잡힘

약 2분 30초에 제품 39개, 그중 9개는 1~4장·면 없음. PD가 1초 넘게 놓쳐 쪼개짐 · PD 오탐 · 패킷 손실로 인한 프레임 공백 중 무엇인지 가르지 못했다. PD는 한 장 11ms로 모든 프레임에 돌았다(속도 문제 아님). 제품 수를 정해 다시 시험한다.
