1. 개요 · 범위

확정

목표: HMD 카메라 영상을 폰이 받아 엣지 서버로 실시간 중계하고, 엣지가 돌려준 판정을 폰 상태기계(C3)에 넣는 길을 완성한다. 엣지는 당분간 개발자 PC(로컬)에서 도는 모의 서버로 시험한다.

단계 구분

단계영상 형식 · 전송상태
이번 (E1)HMD MJPEG(JPEG 프레임 연속, 640×480 · 약 14fps) → 폰 → WebSocket → 로컬 PC 엣지이 설계서 범위
다음 (E2)HMD H.265 1080p 인코딩 → 전송을 WebRTC로 교체 (MA-04)Transport 인터페이스만 갈아끼움
MJPEG도 실시간 영상이다. JPEG 사진을 초당 약 14장 연달아 흘려보내는 방식이라 지연은 짧고, H.265 대비 단점은 용량뿐이다(640×480에선 부담 없음). 엣지 AI는 어차피 프레임을 한 장씩 풀어 판정하므로 E1 시험에는 오히려 다루기 쉽다.

이번 범위 (E1)

  • HMD: MJPEG 각 프레임에 순번·촬영시각 헤더 추가 (작은 변경)
  • 모바일: C2 StreamRelay — HMD MJPEG 수신 → 메타데이터 부착 → WebSocket으로 엣지 송신, 엣지 판정 수신 → Event.JudgeResult → 상태기계
  • 모바일: M-01 "검사 시작"이 InspectionService를 띄우고 교대를 시작하도록 배선 (빈 껍데기 RelayService 정리)
  • 엣지(신규): TacitQEdgeServer (Python) — 영상 수신 · 브라우저 실시간 보기 · 통계 · 가짜 판정 회신

범위 밖

  • 실제 AI 추론(게이팅·면 분할·앙상블) — 모의 엣지는 가짜 판정
  • 판정이 HMD 화면까지 가는 것 — 폰의 실제 BLE 연결(C1 BleLink)이 필요. 이번엔 폰 로그·알림으로 확인, C1에서 연결
  • HMD 로컬 링버퍼·소급 판정(UPLOAD_REQ), Wi-Fi Direct

3. 전송 규격 (WebSocket) — 폰 ↔ 엣지

확정

엣지 팀 규격서가 없어(개발가이드 §0 "Edge 팀 규격서 참조") 이번에 초안을 정한다. 실제 엣지가 생기면 이 문서를 기준으로 맞춘다.

연결

항목값
주소ws://<엣지>:8765/v1/stream
세션교대 1회 = 세션 1개. 폰이 연결 직후 HELLO를 보내고, 끊겼다 다시 붙으면 같은 session_id로 HELLO
방향별 형식폰→엣지 영상 = 바이너리 메시지 · 그 외 제어 = JSON 텍스트 메시지 (type 키로 구분)

① HMD → 폰: MJPEG 파트 헤더 (추가)

--frame
Content-Type: image/jpeg
Content-Length: 41230
X-Seq: 1532                 ← HMD 프레임 순번 (앱 시작부터 1씩)
X-Captured-At: 1727851234567 ← HMD 시계 epoch ms (참고용)

② 폰 → 엣지: FRAME (바이너리)

[4바이트 빅엔디언: 헤더 길이 N][헤더 JSON N바이트 UTF-8][JPEG 원본 바이트 — 손대지 않음]

헤더 JSON 예:
{"seq":1532, "hmd_seq":1532, "captured_at":1727851234567, "received_at":1727851234611,
 "codec":"jpeg", "bytes":41230}
필드뜻
seq폰이 붙이는 세션 내 프레임 순번(끊김 없이 1씩). 엣지 판정이 "몇 번~몇 번 프레임으로 판정했는지"를 이걸로 가리킨다
hmd_seq · captured_atHMD가 준 값 그대로 (HMD 시계)
received_at폰이 HMD에서 받은 시각 (폰 시계)

③ 폰 → 엣지: HELLO (텍스트)

{"type":"HELLO","session_id":"S-20261002-0930-A","line":"A","part_no":"PRS-4410",
 "view_total":3,"codec":"jpeg","app":"TacitQualityMobile 0.x"}

④ 엣지 → 폰 (텍스트)

type언제필드
HB1초마다{"type":"HB","recv_frames":8123,"fps":14.2,"queue":0} — 폰 건강검사의 근거. 3초 무소식 → EdgeUnreachable(R17)
JUDGE부품 판정 완료
{"type":"JUDGE","seq":12,"part_id":"A_0249","verdict":"FAIL","severity":"CRITICAL",
 "confidence":0.93,"agree_rate":0.75,"evidence":"찍힘 · 2면(하면) 좌상단 · 4장 중 3장 검출",
 "frame_ref":"S-20261002-0930-A/1498.jpg","bbox":[0.31,0.22,0.07,0.06],
 "frame_seq_start":1440,"frame_seq_end":1532}
seq = 엣지 판정 순번(세션 내 단조 증가 → 상태기계 R06 근거). verdict = PASS|FAIL|REVIEW. bbox 정규화 [x,y,w,h]
PATTERN연속 불량{"type":"PATTERN","level":"WARN","defect_type":"DENT","hit":5,"window":20} → Event.PatternAlert(R13)
TRAY시험용{"type":"TRAY","part_id":"A_0001","kind":"NG"} → Event.TrayDetected(R08). 모의 엣지 [확인] 버튼 = 트레이 센서 대역 (2026-10-05 추가)

지연(R05) 계산 — 시계 맞추기 없이

상태기계는 delay = arrivedAt − capturedEndAt로 "결과가 늦었나"(1.5초)를 본다. HMD·폰·PC 시계는 서로 어긋나므로 폰 시계 하나만 쓴다: 폰은 보낸 프레임마다 seq → received_at을 기억하고(최근 30초), JUDGE가 오면 capturedEndAt = received_at[frame_seq_end], arrivedAt = 지금. HMD→폰 구간(수십 ms)만 빠지고 나머지(중계·엣지·회신)는 정확히 잡힌다.

4. 모바일 C2 StreamRelay

확정

파일 (패키지 kr.co.snail.tacitq.mobile.relay)

파일내용
Frame.ktdata class Frame(seq, hmdSeq, capturedAt, receivedAt, jpeg: ByteArray) + FRAME 바이너리 직렬화
MjpegReader.kt순수 Kotlin multipart 파서(InputStream → Frame 흐름). 단위시험 대상
HmdVideoSource.ktHTTP로 HMD :8080 연결 → MjpegReader. 끊기면 5초 후 재연결
Transport.kt개발가이드 §5 인터페이스 확장: open(url), sendFrame(bytes), sendText(json), incoming: Flow<String>, isHealthy, close()
WebSocketTransport.ktOkHttp WebSocket 구현 (의존성 추가: com.squareup.okhttp3:okhttp:4.12.0)
StreamRelay.kt큐 · 송신 루프 · 수신 루프 · 건강검사 · seq→received_at 기억. 엔진에 이벤트 발행
EdgeMessages.ktJUDGE/PATTERN/HB JSON → Event (kotlinx.serialization, snake_case 고정)

동작 규칙 (개발가이드 §5 준수)

상황동작
평상시프레임을 손대지 않고(재압축·리사이즈·솎아내기 금지) 메타만 붙여 순서대로 송신
엣지 느림큐 적재(최대 900프레임 또는 64MB). 90% 넘으면 Event.RelayOverflow → 작업자 알림. 몰래 화질 낮추지 않음
큐 가득새 프레임 버리고 버린 수를 기록(M-06 프레임 드롭률)
엣지 3초 무소식(HB 없음)Event.EdgeUnreachable → DEGRADED(R17). 큐 적재 계속
재연결5초 고정 주기 무한 재시도(지수 백오프 금지). 붙으면 같은 session_id로 HELLO → Event.EdgeRecovered(R18) → 큐를 순서대로 송신
JUDGE 수신→ Event.JudgeResult(지연 계산은 §3) → InspectionEngine.send()

서비스 배선

  • InspectionService: onCreate의 TODO(C1/C2) 자리에서 relay.start()를 ioScope로 실행. 포그라운드 타입에 dataSync 추가(개발가이드 요구)
  • M-01 "검사 시작" → InspectionService 시작 + Event.ShiftStarted(line, partNo, profile). "교대 마감" → ShiftClosed + 서비스 종료
  • 기존 relay/RelayService.kt·DualQueue.kt(빈 껍데기, 가장 오래된 것 몰래 버림 — 가이드 위반) 삭제, Manifest 정리
  • M-01에 개발용 "연결 설정"(HMD IP · 엣지 주소) — SharedPreferences 저장. 화면에 중계 상태(송신 fps · 큐 · 엣지 연결) 한 줄 표시

8. E2 — H.265 1080p 전환

구현 완료 · 기본값 보류 (2026-10-07)

목표: HMD 영상을 MJPEG 640×480 → H.265(HEVC) 1920×1080 · 30fps · 약 8Mbps로 전환. HMD 하드웨어 인코더로 압축해 HMD 처리 부담(현재 720p JPEG에서 약 20fps 한계)을 없앤다.

운영 기본값: MJPEG 1280×720(약 22fps). H.265 1080p는 구현·실장비 검증 완료, 필요 시 HMD 설정으로 전환.

사전 확인 (2026-10-07, RealWear 520 실장비)

  • 하드웨어 HEVC 인코더 OMX.qcom.video.encoder.hevc (Qualcomm bengal)
  • 카메라 1920×1080 출력, 30~60fps 범위 지원

결정 (설계서에 없는 부분은 가장 쉬운 방법)

항목결정
전송 방식지금 경로 그대로(HMD HTTP → 폰 → WebSocket → 엣지). 설계의 WebRTC는 보류 — 같은 망 시험에선 지연 차이가 작고 작업량이 큼
HMD 촬영CameraX → Camera2 직접: 출력 2개(화면 미리보기 + 인코더 입력 표면). 녹화용 표준 구성(TEMPLATE_RECORD)
인코딩MediaCodec HEVC, 1920×1080 · 30fps · 8Mbps · 키프레임 1초마다. 키프레임마다 코덱 설정(VPS/SPS/PPS)을 붙여 아무 때나 붙은 수신자도 1초 안에 화면 복원
HMD → 폰 규격지금 multipart 그대로, 파트 1개 = 프레임 1개(HEVC Annex-B). 헤더 Content-Type: video/hevc · X-Seq · X-Captured-At · X-Key(키프레임 1/0)
폰압축 풀지 않고 그대로 중계(지금과 같음). FRAME 헤더에 codec:"hevc" · key 추가. 폰 쪽 변경 최소
엣지PyAV(ffmpeg)로 HEVC 디코딩 → 대시보드용 JPEG(초당 10장) · 녹화(.h265 원본 저장). JPEG 프레임도 계속 받음(코덱 자동 구분)
예비MJPEG 경로 코드는 남겨 두고 HMD 설정으로 전환 가능 — HEVC 문제 시 즉시 되돌림

9. 실제 엣지(AI 서버) 연동 — WebRTC

확정 (2026-10-10) — 1차 구현 중

범위: 우리 역할은 HMD 영상을 폰을 거쳐 엣지(AI 서버)까지 보내고, 엣지가 돌려준 판정을 HMD에 표시하는 것까지. 판정은 엣지가 한다. 엣지 = AI 판정 서버 192.168.1.11 (A4 용지 결함 가모델, 담당 백두용). 근거 문서: 01.암묵지_모바일개발/A4_WEBRTC_API.md. 최종 구성은 HMD → 폰 → AI 서버 (PC 없음).

경로

HMD 카메라 720p ─MJPEG(HTTP, 지금 그대로)─▶ 폰: JPEG 풀기 → WebRTC 영상 트랙(VP8) ─▶ AI 서버 :8080 (POST /offer)
                                              ◀── 데이터 채널(JSON): searching · hold · captured · result · alert
폰 상태기계 ─BLE─▶ HMD 화면 (합격 · 불합격 · 통신불량)

결정 (설계서에 없는 부분은 가장 쉬운 방법)

항목결정
전송WebRTC(:8080)로 바로. 기존 모의 엣지(WebSocket :8765) 경로는 그대로 두고, 폰 설정에서 엣지 종류(모의 엣지 / AI 서버)를 고른다
WebRTC 라이브러리io.getstream:stream-webrtc-android (구글 libwebrtc 빌드) · 소프트웨어 VP8 인코더(EGL 불필요)
영상 원천HMD는 바꾸지 않음 — MJPEG 1280×720 그대로. 폰이 JPEG를 풀어(I420) WebRTC 트랙으로 보냄. 초당 최대 10장(서버 hold 간격 0.2초 → 충분), 밀린 프레임은 버림
해상도 유지WebRTC가 대역폭 부족 시 해상도를 낮추지 않도록 MAINTAIN_RESOLUTION · 최대 비트레이트 6Mbps
HMD 화질720p로 먼저 실제 A4 시험. too_small만 계속 나오면 그때 HMD 해상도를 올린다(§8 H.265 1080p 재사용 또는 MJPEG 1080p)
신호 교환데이터 채널을 offer 전에 열고, ICE 수집 완료 후 POST /offer {sdp,type,station_id:"ST-02"} → answer
판정 매핑result.decision: OK → 합격 · NG → 불합격 · REVIEW → 불합격(§판정 3가지). 부품 ID = result_id(그대로 저장), 순번(seq)은 폰이 부여
지연captured 수신 시각 → result 수신 시각 (폰 시계)
통신불량 · 엣지생존 신호가 없으므로 연결 상태 disconnected/failed/closed → 엣지 통신불량, 5초 주기 새 POST /offer. 422·403은 설정 오류(재시도 안 함, 화면에 표시), 503·접속 실패는 재시도
끊긴 사이 판정captured 후 result 전에 끊기면 재연결 뒤 GET /results/{id} 1초 간격 조회(done → 판정 반영 / failed → 버림)
진행 안내1차: 폰 화면(검사·영상 탭)에 서버 상태 표시(종이 없음 · 더 가까이 · 수집 n/10 · 판정 중). HMD 안내 줄은 2차
연속 알림alert → 반장 알림 기록(화면·진동 없음, 앱은 따로 세지 않음)
사람 판정 보고2차 — POST /results/{id}/decision (트레이 → tray, 시간 초과 → timeout). 1차는 조회 API만
연결 설정M-01 개발용 설정: 엣지 종류 · AI 서버 주소 http://192.168.1.11:8080 · 스테이션 ST-02
