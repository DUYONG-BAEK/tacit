1. 개요 · 범위

현재 기준 (2026-11-09)

목표: 작업자가 HMD(RealWear Navigator 520)를 쓰고 제품을 손에 든 채 돌려 보면, AI 서버가 프레임마다 결함을 찾아 HMD 화면과 폰 화면에 바로 표시하고, 제품 하나가 끝날 때마다 합격·불합격을 판정해 기록한다. 작업자는 수동 모드에서 제품마다 판정이 맞았는지 피드백을 넣고, 이 피드백이 학습 라벨이 된다.

역할 분담

기기하는 일하지 않는 일
HMD카메라 영상 송출(MJPEG 4:3 1920×1440, 초당 12장) · 폰이 BLE로 보낸 화면 표시(판정 글자 · 결함 원 · 면 칩 · 제품 결과) · 폰이 3초 동안 아무 쪽지도 보내지 않으면 스스로 "수동 판정" 화면판정 · 기록
모바일HMD 영상을 받는 대로 AI 서버로 중계(WebRTC) · 서버 메시지를 HMD(BLE)와 폰 화면에 표시 · 작업자 피드백을 서버로 전달 · 서버 이력·사진·디스크 조회 · 통신 로그계산·판정 — 서버 값을 그대로 쓴다. PD·QI 임곗값도 서버가 정한다
AI 서버(엣지)PD(제품 탐지) → QI(불량 탐지) 프레임 판정 · 제품 구간 · 결함 확정 · 제품 판정 · 면 진행 · 사진·DB 기록 · 이력·피드백·디스크 API영상 표시 · 학습(모델은 서버 밖에서 학습해 .pt만 가져온다)

작업자 사용 흐름

#작업자시스템
1HMD 전원을 켠다HMD 앱이 뒤에서 떠 BLE 광고 (화면은 홈 그대로)
2폰 핫스팟을 켜고 사내 Wi-Fi에도 연결HMD는 핫스팟, 서버는 사내 Wi-Fi로
3폰 M-01에서 모드(수동·자동) 확인 → 검사 시작폰이 BLE로 HMD를 찾아 붙고(HMD 영상 주소를 HELLO로 받음), HMD 영상과 AI 서버 연결을 연다. HMD 앱이 앞으로 나와 카메라를 켜고, 폰은 M-07 영상 화면으로 넘어간다
4제품을 들고 멈추지 않고 천천히 돌려 본다HMD 가운데 "검사 중" · 결함 프레임이면 ✕ 불합격(빨강)·? 애매(노랑) + 결함 위치 원 · 아래 면 칩 줄(■ 상면 □ 엣지 □ 하면비닐)
5제품을 내려놓는다1초 뒤 서버가 제품을 끝내고 판정 → HMD에 "✓ 합격"·"✕ 불합격 · 결함 종류" 2초, 폰에 결과 카드, 불합격이면 폰 진동 3회
6(수동 모드) 폰에서 맞음·틀림·확인필요서버에 피드백 저장. 누르지 않고 다음 제품으로 가면 "미입력"으로 남는다
7M-01에서 교대 마감HMD에 대기 화면을 보낸 뒤 연결을 끊는다(HMD는 장애로 보지 않음)
8M-05 이력에서 미입력·확인필요를 정리서버 기록을 조회, 프레임 사진 넘겨 보기·결함 확대, 피드백 수정(변경 기록이 남음). M-06에서 서버 디스크

범위 밖 (지금)

  • 인증·HTTPS (같은 사내망 전제, 피드백은 누구나 수정 가능)
  • 사람의 최종 판정 절차(끄덕임·가로젓기·트레이) — 서버 규격에서 없어졌다. 코드는 호출만 끊어 두었다(HMD 수동 판정 화면의 제스처 안내도 표시만)
  • H.265 전송 — 구현했으나 기본값 보류 (4장)
  • 해상도별 검출률 비교, HMD → 폰 → 서버 → HMD 구간별 지연 실측
  • M-01 점검 6항목, M-02~M-04, M-06 지표 — 화면 예시 데이터

네트워크

  • HMD는 폰 핫스팟, 폰과 서버는 사내 Wi-Fi(192.168.1.0/24, 개발 서버 192.168.1.11). 폰은 두 망에 동시에 붙는다

  • 평문 HTTP·WS — 안드로이드 cleartext 예외 설정 필요

3. AI 서버 연동 — 판정 · 메시지 · 화면

2026-11-06 규격 · 2026-11-09 개발 서버 배포·실측

원칙: 계산과 판정은 모두 AI 서버가 한다. 폰은 영상을 넘기고, 서버가 보낸 값을 HMD·폰 화면에 그대로 보이고, 작업자 피드백을 서버로 전한다. 규격은 server/A4_WEBRTC_API.md(앱 연동), 판정 규칙·설정값은 server/DEPLOY.md §3.

판정 규칙 (서버)

단계규칙
제품 탐지 (PD)프레임마다 전체를 640으로 줄여 PD. 상자가 하나라도 있으면(엣지·상면·하면비닐 중, 신뢰도 0.4 이상) 그 프레임을 QI로. 없으면 searching. 크기·위치 조건은 없다
불량 탐지 (QI)같은 프레임 전체를 640 타일(간격 512)로 덮어 추론 → 결함 상자의 중심이 PD 상자 안인 것만 남긴다(배경 오탐 제거)
프레임 판정점수 = 남은 결함의 최대 신뢰도. 기준값 T = 0.4(임시) → T×1.1 초과 NG, T×0.9 미만 OK, 사이는 REVIEW(애매)
제품 구간첫 제품 프레임에서 시작, 마지막 제품 프레임 뒤 1초 동안 제품 프레임이 없거나 연결이 끊기면 끝. searching 한 장은 끝내지 않는다
결함 확정 · 제품 판정구간 안 최근 5장 중 2장 이상 NG·REVIEW면 확정(NG가 있으면 NG, 나중에 NG로 올라갈 수 있다). 확정 없음 → PASS, 있음 → FAIL(REVIEW 확정도 FAIL)
면 진행PD 라벨별로 그 제품에서 잡힌 프레임 수. 5장 이상이면 그 면을 본 것(2026-11-09 3 → 5, 확정 창과 맞춤). 모두 보면 complete — 판정·구간에는 영향 없음
저장제품 프레임 전부 사진(JPEG 90) · 결함 프레임은 연결마다 1초에 1장 오버레이(result_id) · 연결마다 설정값·통계(sessions.config·stats)

4. E2 — H.265 1080p 전환 (보류)

구현 완료 · 기본값 보류 (2026-10-07)

목표: HMD 영상을 MJPEG 640×480 → H.265(HEVC) 1920×1080 · 30fps · 약 8Mbps로 전환. HMD 하드웨어 인코더로 압축해 HMD 처리 부담(현재 720p JPEG에서 약 20fps 한계)을 없앤다.

운영 기본값: MJPEG 1280×720(약 22fps). H.265 1080p는 구현·실장비 검증 완료, 필요 시 HMD 설정으로 전환.

사전 확인 (2026-10-07, RealWear 520 실장비)

  • 하드웨어 HEVC 인코더 OMX.qcom.video.encoder.hevc (Qualcomm bengal)
  • 카메라 1920×1080 출력, 30~60fps 범위 지원

결정 (설계서에 없는 부분은 가장 쉬운 방법)

항목결정
전송 방식지금 경로 그대로(HMD HTTP → 폰 → WebSocket → 엣지). 설계의 WebRTC는 보류 — 같은 망 시험에선 지연 차이가 작고 작업량이 큼

인코딩MediaCodec HEVC, 1920×1080 · 30fps · 8Mbps · 키프레임 1초마다. 키프레임마다 코덱 설정(VPS/SPS/PPS)을 붙여 아무 때나 붙은 수신자도 1초 안에 화면 복원
HMD → 폰 규격지금 multipart 그대로, 파트 1개 = 프레임 1개(HEVC Annex-B). 헤더 Content-Type: video/hevc · X-Seq · X-Captured-At · X-Key(키프레임 1/0)

부록 A. E1 개요 · 범위 (모의 엣지 단계)

E1 기록 (2026-10) — 현재 기준 아님
부록 A~G는 2026-10 E1 단계(모의 엣지 · WebSocket) 설계 기록이다. 지금 시스템은 1~4장을 본다. 모의 엣지 경로는 앱에 남아 있다(M-01 엣지 종류 "모의 엣지", relay/StreamRelay). 부록 안의 장 번호(§3 등)는 옛 번호다 — 옛 3~7장 = 부록 C~G.

단계 구분

단계영상 형식 · 전송상태
이번 (E1)HMD MJPEG(JPEG 프레임 연속, 640×480 · 약 14fps) → 폰 → WebSocket → 로컬 PC 엣지이 설계서 범위

MJPEG도 실시간 영상이다. JPEG 사진을 초당 약 14장 연달아 흘려보내는 방식이라 지연은 짧고, H.265 대비 단점은 용량뿐이다(640×480에선 부담 없음). 엣지 AI는 어차피 프레임을 한 장씩 풀어 판정하므로 E1 시험에는 오히려 다루기 쉽다.
